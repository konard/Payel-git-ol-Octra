# Octra — финальная концепция

## Суть

Octra — MCP агрегатор. Мы не производим AI, не пишем своих агентов. Мы даём возможность запускать готовые AI CLI (claude code, opencode, codex и т.д.) с настроенными скиллами на нашей инфраструктуре — без SSH, без аренды сервера, без танцев с бубном.

Каждый пользователь получает **свой персональный MCP эндпоинт**, к которому можно обращаться по API.

---

## Проблема

Вайбкодеры и AI-юзеры — люди из разных сфер. Настройка MCP сервера требует:
- аренды VPS
- SSH
- установки зависимостей
- написания JSON конфигов
- понимания портов, процессов, systemd

Этот порог большинство не перешагивает. Они либо забивают, либо теряют дни.

## Аудитория

- Вайбкодеры — хотят AI с инструментами без танцев с бубном
- Фрилансеры — нужен AI помощник 24/7
- Команды — хотят расшарить одного агента
- Все, кто устал настраивать MCP вручную

**Что убираем:**
- user сервис
- agents сервис
- orchestrator
- apigateway
- промты босса/менеджера/воркера
- все иерархии агентов

**Что не трогаем:**
- frontend
- poster
- tgbot

- Docker Compose: бэкенд + PostgreSQL + Redis
- Nix для изоляции окружений пользователей
- Каждый пользователь → свой Nix profile с установленными CLI и скиллами

## Воркфлоу

### 1. Регистрация

Пользователь регистрируется на платформе, получает `api_key`.

### 2. Создание окружения

POST `/environment`:

```json
{
  "llm": {
    "api_key": "sk-...",
    "base_url": "https://api.anthropic.com"
  },
  "agent": {
    "cli": "claude-code"
  },
  "skills": ["filesystem", "github", "brave-search"]
}
```

Ответ:
```json
{
  "user_id": "",
  "api_key": ""
}
```

Что происходит:
1. Создаётся Nix окружение пользователя
2. Устанавливается CLI (если указан)
3. Устанавливаются и настраиваются скиллы в этом окружении
4. Если CLI не указан — Octra будет работать как простой прокси к LLM

### 3. Использование

Запрос к агенту:

```bash
curl http://localhost/api/chat \
  -H "octra-api-token: $OCTRA_API_KEY" \
  -H "Content-Type: application/json" \
  -X POST \
  -d '{
    "prompt": "напиши код для парсинга csv",
    "skills": ["filesystem"]
  }'
```

Ответ:
```json
{
  "response": "вот ..."
}
```

### Flow запроса

```
запрос → валидация токена → поиск пользователя и его агента
→ если есть CLI:
    → проверить Redis: жив ли процесс?
      → если жив → отправить промпт в stdin
      → если мёртв → запустить subprocess в Nix env
    → иначе:
    → прямой вызов LLM с инструментами (скиллами)
→ получить ответ → вернуть пользователю
```

## Управление CLI процессами

- CLI запускается как subprocess внутри Nix окружения пользователя
- Процесс **не убивается после каждого запроса**
- Состояние процесса хранится в Redis:
  - `user:{id}:cli_state` — PID, порт (если HTTP), время запуска
  - `user:{id}:cli_ttl` — TTL процесса
- При запросе проверяется Redis: жив ли процесс?
  - Жив → используем
  - Мёртв (TTL истёк / упал) → перезапускаем
- По истечении TTL процесс принудительно убивается

### Способы коммуникации с CLI

- **По умолчанию: stdin/stdout pipe** — быстрее, нативно для AI CLI
- Если конкретный CLI поддерживает HTTP-режим — можно через него

---

## Скиллы

- Скиллы — это готовые пакеты из nixpkgs или кастомные конфигурации
- Пользователь выбирает скиллы на канве (фронтенд)
- Скиллы устанавливаются в Nix окружение пользователя
- При запросе можно **отключить** скилл, не включая его в поле `skills[]`
- Способ установки каждого скилла хранится в БД

## Модели данных

### User
- ID, email, password hash
- Дата регистрации
- Статус подписки

### Agent (Environment)
- ID
- UserID (владелец)
- LLM конфиг (api_key, base_url, model)
- CLI (опционально)
- Статус (активен/неактивен)

### Skill
- ID
- Название
- Тип (built-in / nixpkgs / custom)
- Способ установки (команда / конфиг)
- Описание

### UserSkill
- UserID
- SkillID
- AgentID
- Статус установки
